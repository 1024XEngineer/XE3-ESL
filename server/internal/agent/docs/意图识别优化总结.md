# 意图识别优化总结

## 背景

SpeakUp 的 Agent 需要根据用户自然语言请求，在“直接语言帮助”和“业务工具调用”之间做稳定路由。优化前，系统虽然已经接入 Review、Material、Mistake、Scenario 等工具，但在强业务意图下仍存在模型不调用工具、上下文引用误判、写工具确认边界不清晰等问题。例如“帮我找一下上次 PM interview 的 review”容易因“上次”被退化为泛化上下文缺失，导致工具候选变宽或模型直接回答。

## 优化目标

- 提升历史 Review、简历/JD 材料、错题记录等强业务意图的识别稳定性。
- 将路由结果从简单 `reason_code` 升级为可观测、可测试的结构化决策。
- 让 Runtime 能明确表达“本轮必须/优先调用哪个工具”，减少模型自由选择导致的不稳定。
- 对创建场景等写操作引入确认型路由，避免未确认时直接执行写工具。
- 通过真实 HTTP 链路验证前端同路径用户消息的端到端行为。

## 核心改动

### 1. 引入结构化 RouteDecision

新增结构化路由结果，包含：

```text
intent
confidence
has_context_reference
tool_use_mode
preferred_tools
reason_code
router_version
```

将 `language_help`、`historical_review`、`material_context`、`historical_mistake`、`scenario_create`、`scenario_search` 等意图显式建模，并保留旧的 `IntentDecision`、`ReasonCode` 和 manifest 字段，保证 HTTP 与持久化结构向后兼容。

### 2. 调整意图判断顺序

将原先“先判断上下文引用”的逻辑改为：

```text
先识别业务域信号 -> 再标记上下文引用 -> 组合生成 RouteDecision
```

这样“上次 / 之前 / previous / last time”等词不会覆盖 Review、Mistake 等高价值业务意图。例如：

```text
帮我找一下上次 PM interview 的 review
-> historical_review
-> has_context_reference=true
-> preferred_tools=["review.search.v1"]
```

### 3. 增加 provider-neutral ToolChoice

在 `ai.TextRequest` 中新增中立工具选择契约：

```text
none
auto
required
specific(tool_name)
```

Runtime 根据 `RouteDecision` 设置 `ToolChoice`：

- 翻译、润色、表达建议：`none`
- 历史 Review：`specific(review.search.v1)`
- 简历/JD/材料：`specific(material.search.v1)`
- 错题记录：`specific(mistake.search.v1)`
- 创建场景：`confirm_required`，未确认时 `none`

千问适配器负责把中立 `ToolChoice` 映射为 provider 协议，避免业务 Runtime 直接依赖供应商私有结构。

### 4. 强业务意图工具调用保护

对 `historical_review`、`material_context`、`historical_mistake` 等强业务意图，工具可用时要求模型优先调用指定工具。如果模型忽略 specific tool choice 直接回答，Runtime 会返回保守 fallback，避免编造用户历史数据。

### 5. 场景创建确认型路由

将“创建英文后端面试练习场景”识别为：

```text
route_intent=scenario_create
tool_use_mode=confirm_required
preferred_tools=["scenario.create.v1"]
```

由于 `scenario.create.v1` 是写工具，未确认时不会暴露给模型执行。当前阶段先完成路由、日志和策略拦截，后续可继续补完整确认流。

### 6. 修复真实联调中的供应商兼容问题

HTTP 联调时发现千问兼容模式可能返回：

```text
finish_reason=stop
message.tool_calls 非空
```

旧适配逻辑只接受 `finish_reason=tool_calls`，导致强业务工具调用被误判为 `invalid_response`。已在千问 adapter 中将“存在 tool_calls 的 stop 响应”归一为内部 `tool_calls`，并补充回归测试。

### 7. 修复空 source_refs 持久化

工具执行成功但无命中结果时，`source_refs` 统一持久化为空数组 `[]`，避免 nil 被写为 `null` 后引发状态误判或约束问题。

## HTTP 联调结果

启动方式：

```bash
cd server
SERVER_HOST=127.0.0.1 AGENT_TOOL_MODE=real AGENT_TOOL_FIXTURES=1 go run ./cmd/server
```

通过真实前端同路径接口验证：

```text
POST /v1/auth/register
POST /v1/auth/login
POST /v1/agent-threads
POST /v1/agent-threads/:thread_id/runs
GET  /v1/agent-runs/:run_id/context-manifest
GET  /v1/agent-threads/:thread_id/messages
```

验证结果：

| 用户输入 | 路由结果 | 工具策略 | 实际行为 |
| --- | --- | --- | --- |
| 帮我找一下上次 PM interview 的 review | `historical_review` | `specific(review.search.v1)` | 调用 `review.search.v1` 后回答 |
| 结合我的简历和后端岗位 JD，帮我准备英文自我介绍 | `material_context` | `specific(material.search.v1)` | 调用 `material.search.v1` 后回答 |
| 看一下我以前的错题，找 recurring mistakes | `historical_mistake` | `specific(mistake.search.v1)` | 调用 `mistake.search.v1` 后回答 |
| 帮我创建一个英文后端面试练习场景 | `scenario_create` | `confirm_required` / `none` | 不执行写工具，直接生成回复 |
| 把“我负责后端稳定性”翻译成自然英文 | `language_help` | `none` | 不暴露工具，直接回答 |

## 测试覆盖

新增和扩展了确定性单元测试，覆盖：

- 结构化路由决策；
- 上下文引用不覆盖业务意图；
- ToolPolicy 候选工具收窄；
- provider-neutral `ToolChoice` 校验；
- 千问 `tool_choice` payload 映射；
- 千问 `finish_reason=stop` 但含 tool calls 的兼容；
- 强工具意图未调用工具时的保守 fallback；
- 空 `source_refs` 持久化为空数组。

验收命令：

```bash
cd server
go test ./internal/agent/runtime ./internal/agent/tool ./internal/ai ./internal/ai/qianwen
```

## 简历表述参考

- 负责优化 AI 英语陪练 Agent 意图路由链路，设计并落地结构化 `RouteDecision`，将历史复盘、简历/JD、错题、场景创建、语言润色等意图显式建模，提升业务工具调用稳定性。
- 引入 provider-neutral `ToolChoice` 契约，将 Runtime 工具选择与模型供应商协议解耦，并在千问适配层完成 tool calling 映射与兼容处理。
- 重构上下文引用识别顺序，解决“上次/之前/继续”等表达导致 Review、Mistake 等业务意图退化的问题，实现强业务意图下指定工具优先调用。
- 建立 Agent 路由确定性测试与 HTTP 端到端联调流程，验证 `review.search.v1`、`material.search.v1`、`mistake.search.v1` 等工具在真实用户消息链路中的稳定触发。
- 修复千问兼容模式 `finish_reason=stop` 但返回 tool calls 导致的响应误判，并补充回归测试，提升模型工具调用链路鲁棒性。

## 后续优化方向

- 为 `confirm_required` 场景补完整确认状态机，避免用户看到“像已创建”的自由回复。
- 将 `RouteDecision` 输出扩展到 context manifest API，便于前端和运维直接观测路由结果。
- 后续可引入 embedding/semantic router，替代部分关键词规则，提高长尾表达覆盖率。
